# პაციენტის კომუნიკაციის რეესტრი — GitHub Pages + Supabase

ეს პროექტი ქმნის ონლაინ ფორმას, თვიურ შემაჯამებელ რეესტრს, სრულ ჩანაწერებს და როლებზე დაფუძნებულ წვდომას.

## როლები

- `doctor` — ქმნის ჩანაწერს და ხედავს მხოლოდ თავის შექმნილ ჩანაწერებს.
- `reviewer` — ხედავს ყველა ჩანაწერსა და თვიურ ცხრილს.
- `admin` — ხედავს ყველაფერს და მართავს მომხმარებლის როლსა და აქტიურ სტატუსს.

## უსაფრთხოების მნიშვნელოვანი საზღვარი

GitHub Pages ინახავს მხოლოდ საჯარო ვებკოდს. პაციენტის მონაცემები ინახება Supabase-ის PostgreSQL ბაზაში და იცავს Row-Level Security. არასოდეს ჩაწეროთ `service_role` გასაღები GitHub-ში, `.env`-ში ან ბრაუზერის კოდში. გამოიყენეთ მხოლოდ `Publishable key` (ან ძველი პროექტის `anon` key).

რეალურ კლინიკურ გამოყენებამდე ორგანიზაციამ უნდა შეაფასოს საქართველოს პერსონალურ მონაცემთა დაცვის მოთხოვნები, მონაცემთა დამუშავების ხელშეკრულება, მონაცემთა მდებარეობა/რეგიონი, შენახვის ვადა, ინციდენტებზე რეაგირება, სარეზერვო ასლები, MFA და აუდიტის ჟურნალი. სატესტო ეტაპზე გამოიყენეთ მხოლოდ გამოგონილი მონაცემები.

## 1. Supabase-ის მომზადება

1. გახსენით `https://supabase.com` და შექმენით ახალი პროექტი შესაბამის რეგიონში.
2. პროექტში გახსენით **SQL Editor → New query**.
3. ჩასვით `supabase/schema.sql` და გაუშვით.
4. გახსენით **Authentication → Users → Add user** და შექმენით თქვენი ადმინისტრატორის ანგარიში.
5. SQL Editor-ში გაუშვით ფაილის ბოლოში მოცემული `UPDATE`, სადაც `FIRST_ADMIN_EMAIL` შეცვლილია თქვენი ელფოსტით.
6. **Authentication → URL Configuration**-ში `Site URL` მიუთითეთ GitHub Pages-ის საბოლოო მისამართზე, მაგალითად:
   `https://YOUR_GITHUB_NAME.github.io/patient-communication-registry/`
7. **Project Settings → API**-დან დაიმახსოვრეთ:
   - Project URL
   - Publishable key (ან legacy `anon` key)

## 2. ადგილობრივი შემოწმება

```bash
cp .env.example .env
```

`.env` ფაილში ჩაწერეთ:

```text
VITE_SUPABASE_URL=თქვენი_Project_URL
VITE_SUPABASE_PUBLISHABLE_KEY=თქვენი_Publishable_Key
```

შემდეგ:

```bash
npm install
npm run dev
```

ტესტირებისთვის გამოიყენეთ მხოლოდ გამოგონილი პაციენტები.

## 3. GitHub-ზე ატვირთვა

1. GitHub-ში დააჭირეთ **New repository**.
2. სახელად მიუთითეთ `patient-communication-registry`.
3. კლინიკური პროექტისთვის რეკომენდებულია **Private repository**. GitHub Pages-ის ვებკოდი მაინც ჩაიტვირთება მომხმარებლის ბრაუზერში, ამიტომ მასში საიდუმლო გასაღები არ უნდა იყოს.
4. ამ საქაღალდის ყველა ფაილი ატვირთეთ repository-ის ფესვში. Git ბრძანებებით:

```bash
git init
git add .
git commit -m "Initial secure communication registry"
git branch -M main
git remote add origin https://github.com/YOUR_GITHUB_NAME/patient-communication-registry.git
git push -u origin main
```

## 4. GitHub Secrets

Repository-ში გახსენით:

**Settings → Secrets and variables → Actions → New repository secret**

დაამატეთ:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`

Publishable key საიდუმლო ადმინისტრაციული გასაღები არ არის; მონაცემთა რეალურ დაცვას RLS უზრუნველყოფს. მიუხედავად ამისა, GitHub Secret-ის გამოყენება გამორიცხავს მის წყაროში შემთხვევით ჩაწერას.

## 5. GitHub Pages-ის ჩართვა

1. გახსენით **Settings → Pages**.
2. **Build and deployment → Source**-ში აირჩიეთ **GitHub Actions**.
3. გახსენით **Actions** ჩანართი. `Deploy to GitHub Pages` ავტომატურად გაეშვება `main` branch-ზე ატვირთვის შემდეგ.
4. დასრულების შემდეგ მისამართი იქნება დაახლოებით:
   `https://YOUR_GITHUB_NAME.github.io/patient-communication-registry/`

## 6. ექიმებისა და უფლებამოსილი პირების დამატება

1. Supabase-ში გახსენით **Authentication → Users → Add user** ან **Send invitation**.
2. მომხმარებლის შექმნის შემდეგ შედით აპში ადმინისტრატორის ანგარიშით.
3. გახსენით **მომხმარებლები**.
4. მიუთითეთ სრული სახელი, როლი (`doctor`, `reviewer`, `admin`) და აქტიური სტატუსი.
5. `reviewer` ან `admin` მიანიჭეთ მხოლოდ იმ პირებს, ვისაც ყველა პაციენტის ჩანაწერის ნახვის სამართლებრივი და სამსახურებრივი საფუძველი აქვს.

## 7. სამუშაო პროცესი

- ექიმი შედის ელფოსტითა და პაროლით და ავსებს ფორმას.
- ჩანაწერი ავტომატურად ხვდება შესაბამისი თვის რეესტრში.
- თვე იცვლება კალენდარული `YYYY-MM` ფილტრით.
- უფლებამოსილ მომხმარებელს შეუძლია ძებნა, სრული ჩანაწერის გახსნა, CSV ექსპორტი და ბეჭდვა/PDF.
- ადმინისტრატორი მომხმარებლის ანგარიშს ააქტიურებს/თიშავს და ანიჭებს როლს.

## წარმოებაში გაშვებამდე სავალდებულო შემოწმება

- გამორთეთ საჯარო რეგისტრაცია; მომხმარებლები მხოლოდ ადმინისტრატორმა მოიწვიოს.
- ჩართეთ MFA ადმინისტრატორებისა და მიმომხილველებისთვის.
- შეამოწმეთ RLS ცალკე `doctor`, `reviewer` და `admin` ანგარიშებით.
- განსაზღვრეთ ჩანაწერის შენახვისა და წაშლის პოლიტიკა.
- განსაზღვრეთ ვინ და რა საფუძვლით ახორციელებს CSV ექსპორტს.
- ჩაატარეთ კონფიდენციალურობისა და ინფორმაციული უსაფრთხოების შეფასება.
- რეალური მონაცემების შეტანამდე მიიღეთ დაწესებულების იურიდიული/ინფორმაციული უსაფრთხოების წერილობითი თანხმობა.
